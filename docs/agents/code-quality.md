# 代码质量

## 组织

- 按功能和明确职责组织持续增长的区域。
- 每个源码文件聚焦一个主要职责；解析、UI、I/O、编排和验证混杂时进行拆分。
- 手写文件优先控制在 500 行以内；没有具体拆分理由时不得超过 1000 行。
- 生成文件、第三方代码、数据、模板和大型 fixture 不受行数限制。
- 较长文件使用 section marker 区分生命周期、状态、protocol conformance、I/O、解析和私有 helper。

## 命名与实现

- 遵循语言和框架的常规命名。
- Swift 类型和编译的 Swift 文件名使用 `UpperCamelCase`，函数和属性使用 `lowerCamelCase`。
- 不被代码导入的独立脚本、治理文档和导出产物使用 kebab-case。
- 优先使用明确控制流和描述性名称，不追求过度压缩。
- 除非领域需要，避免全局可变状态和类型级 helper。
- 在现有 API 使用异步和 typed error 的位置，优先使用 `async/await` 和 `SelectedTextKitError`。

## 文档与注释

- 仓库治理文档使用中文，代码注释和 API 文档注释使用英文。
- 为公共 API，以及不明显的并发、状态机、I/O 和恢复行为添加文档。
- 不添加只重复显而易见代码的注释。
- 注释保持简洁并随行为更新。
- 保留现有文件头作者信息，不插入 Agent 身份。
